# 场景：排查面试

本次是排查面试（`task.kind = scenario`）。`task.theme` 指定本组题型，只出该题型 1~2 张卡：

- `troubleshoot`：故障排查
- `performance`：性能优化
- `design`：方案设计

只执行与 `task.theme` 对应的题型小节；其他题型小节不要使用。

本节规则覆盖 `cards.md` 中关于 `mainQuestion` 长度与事实边界的要求；追问链、
露馅信号与输出格式仍按 `cards.md` 执行。

## 出题范围

- 先通读 `profile`，判断候选人的主技能 / 主技术栈：
  - `tech_stacks[].level`：精通 > 熟练 > 掌握；
  - 技术在 `projects[].tech_stack` 与项目描述中出现的频率；
  - 与 `direction`（求职方向）是否一致。
- 主技术栈通常 1~3 项。`task.primaryTechs` 是后端按等级与项目使用次数给出的提示，
  优先参考它；如果从项目描述、项目角色里看到更明确的主技术证据，以项目证据为准。
- 至少 2/3 的卡围绕主技术栈出；非主技术最多 1 张卡，不要为了覆盖而平均分配。
- 技术只能来自画像；不能引入画像之外的语言、框架、数据库、中间件、工具或云服务。
- 技能不限于编程。候选人是测试、数据、前端、运维、设计或其他方向时，按该方向
  真实工作中的问题出题，不要硬套后端技术。

## 题目形态

每张卡 = 一个具体场景 + 一个核心问题。

- `mainQuestion` 允许 2~5 句：先用“假设你负责……”交代系统 / 业务背景、规模、现象或
  目标与约束，最后只问一个核心问题。
- 只问一个核心问题；不要把追问写进主问题，也不要一次问“怎么定位、怎么优化、
  怎么预防”三件事。
- 场景必须让候选人能给出可操作的答案：排查步骤、定位手段、数据模型或方案取舍。
- 不得问“你之前遇到过吗”“讲讲你项目里的 X”。排查面试考的是面对场景怎么想、
  怎么做，不是复述经历。
- `projectId` 可以留空；借用具体项目作为背景时填该项目 id。
- `anchorId` 可以留空；有匹配的真实锚点时优先使用，此时 `evidenceQuote` 逐字复制原文。

## 共同约束

- 题目中的指标、流量、数据量可以编造，不需要与简历一致；这是场景设定，不是简历事实。
- 用“假设你负责……”引出场景，不要写成“你之前遇到过”。
- 每张卡至少落回画像里的一项技能 / 技术，不出与技术栈无关的通用题。
- 不考纯八股：可以问原理，但必须放在故障、瓶颈或设计约束里问。
- 不要使用固定的技术故障清单；根据画像里的技能，自行判断这个岗位真实会遇到什么问题。
- 同一组内不要出意思重复的卡；三类题之间尽量覆盖不同技能。
- 只出题，不生成参考答案。

## 追问链

每张卡写 4 条追问，固定 **1 条 L1、1 条 L2、2 条 L3**：

- `L1` 信息收集与第一步：先看什么、先做什么、如何确认现象。
- `L2` 假设与验证：根因 / 瓶颈假设怎么区分，方案怎么取舍。
- `L3` 极端条件：流量突增、数据倾斜、部分失败、扩容或回滚时还成不成立。
- `L3` 验证与复盘：怎么证明有效、怎么防复发、如果重来会改什么。

追问必须顺着主问题自然问出来，同一张卡内不要重复同一个点。

## 露馅信号

`leakSignals` 至少 2 条，必须可操作，例如：

- 直接给结论，没有排查路径；
- 只会给通用手段，没有针对该技能的定位思路；
- 把现象当根因；
- 只看单一证据，不做交叉验证；
- 设计题只画组件或流程，不谈数据模型、唯一性、扩展与失败处理；
- 不谈验证方式与取舍。

## 题型：故障排查（`task.theme = troubleshoot`）

### 场景要求

- 给出一个具体的异常现象和系统 / 业务背景：角色、部署或使用方式、规模（可编造）、
  最近变化、影响范围。
- 现象要指向多个可能根因，不能一眼看出答案。
- 至少加入一个干扰信息或约束，例如规模没有变化、最近没有发布、只有部分实例异常。
- 场景要贴合画像里的技能，让人能给出该技能对应的定位手段。

### 考察重点

1. 先确认现象与影响面，再收集证据：监控、日志、指标、命令或等价手段。
2. 提出 2~3 个根因假设，说明怎么验证、怎么排除。
3. 先止损再根治，说明止损动作的代价。
4. 定位根因后给出修复与预防。

### 禁止

- 不要出无场景的名词解释或背诵题。
- 不要只问“怎么优化”，要问“怎么定位、怎么验证”。
- 不要编造画像里没有的技术或组件。

## 题型：性能优化（`task.theme = performance`）

### 场景要求

- 给出当前表现与目标：延迟、吞吐、资源占用、成本等，数字可以编造。
- 交代系统 / 业务背景、读写或使用模式、规模与约束。
- 至少给出一个约束：不能加资源、不能停机、不能改结构、预算有限等。
- 瓶颈要有多个可能方向，不能一看就知道答案。

### 考察重点

1. 先测量再优化：基线、压测、监控、日志或等价手段。
2. 找到真正的瓶颈，而不是直接背优化清单。
3. 给出方案、预期收益、代价和风险。
4. 说明怎么验证优化有效、怎么回滚。

### 禁止

- 不要直接列通用优化手段。
- 不要在缺少测量的情况下断言瓶颈。
- 不要引入画像里没有的技术。

## 题型：方案设计（`task.theme = design`）

### 场景要求

- 给出明确的业务 / 系统目标，以及可验证的约束，至少包含以下 2~3 项：
  - 规模：用户量、请求量、数据量、增长预期；
  - 唯一性 / 一致性要求；
  - 可用性、延迟、成本；
  - 现有技术边界或不能引入的技术。
- 数字可以编造，但要在题目里交代清楚。
- 技术选型必须从画像已有技能出发，不能默认引入候选人不掌握的技术。
- 题目必须让人能落到数据模型、核心流程、扩展与失败处理，而不只是画组件。

### 考察重点

1. 需求澄清：功能边界、读写 / 使用模式、一致性、增长预期。
2. 数据模型：关键实体、唯一性、索引 / 分片、扩展方式。
3. 核心流程：写入、查询、分配、冲突处理。
4. 扩展与失败：热点、容量、降级、重试、幂等、迁移。
5. 取舍：为什么不用另一种方案，代价是什么。

### 禁止

- 不要只画组件图，不讲数据模型与关键约束。
- 不要问“讲讲你理解的分布式”这类泛题。
- 不要出与候选人技能无关的设计题。
